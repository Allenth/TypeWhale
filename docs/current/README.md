## 产品与基线

TypeWhale Pro 是本地优先的 macOS 桌面语音输入与智能文字处理工具：通过全局快捷键录音，在不抢焦点的胶囊中反馈识别进度，将文本送回目标应用。智能整理、翻译、截图归档、闪念和 OpenClaw 是围绕主流程的扩展。

## 使用与排障入口

1. 本机已安装应用位于 `/Applications/TypeWhale Pro.app`。打开主窗口，按权限提示检查麦克风与辅助功能；截图需相应屏幕录制权限。
2. 查看模型页的下载／就绪状态；怀疑智能整理失效时，在“整理模型”卡片点击“开始检测”，按失败阶段和错误码排查，必要时显式复制脱敏诊断。在快捷键设置中确认实际绑定，不假定所有电脑使用相同默认键。
3. 在备忘录等普通输入框先使用原文模式完成一次录音与写回；之后再开启整理、翻译或自动发送。
4. 本地智能处理的模型与路由见 [架构](ARCHITECTURE.md)；不要按旧 README 启动 Ollama。选择云端处理前检查自己的配置及数据发送边界。
5. 无文本时先看权限、所选模型与识别错误；粘贴异常先检查前台目标和最近转录；OpenClaw 失败先查 CLI/Gateway 与 Node。完整步骤见 [发布与验收](RELEASE_QA.md)。

从源码安装仅使用 `./native/build_and_log.sh`，先完成 [并发和版本检查](RELEASE_QA.md)。该命令会编译、递增 build、覆盖安装并启动，不是只读诊断命令。

## 维护与防止再次失真

- 一个事实一个维护位置。其他文档引用，不复制长规格；版本核验快照集中在本页，机器版本字段和应用历史仍保留。
- 文档日期表示实际审查日期，不通过批量改日期制造新鲜度。每次行为变化在同一提交更新所属文档及开发日志。
- 新目录不会被现有构建脚本自动刷新。发布执行者必须人工核对本页版本快照，不能只更新根 README 的版本字符串。
- 每次交付检查：现行文档是否与实现一致、旧方案是否误写为当前、链接是否可达、测试结果是否有证据。未知事项保留负责人及下一步。
- 开发日志超过预算时，将较早条目移入按月历史文件并在入口保留链接；本轮不移动既有历史档案。


## 以开发日志驱动讨论、提炼和文档同步

开发日志是讨论与过程追溯的主线；各专题文档负责表达提炼后的现行结论。日志日期最新不等于内容已完整：每次 session 先对照近期 Git 提交、构建记录和用户反馈，发现遗漏时补记实际发生日期、补记日期及来源，不能编造过去的验证。

固定流程：**记录 → 讨论 → 提炼 → 核证 → 分流 → 复核**。

1. 记录用户的真实目标、场景、痛点、限制与体验反馈，保留影响产品判断的情绪和优先级，不抄整段聊天。
2. 讨论并记录选择理由、被否定的方案、未解决分歧；区分用户决定和 Agent 建议。
3. 提炼本轮稳定结论及下一步，明确状态：讨论中、已决定、已实现、已验证、已否决或已被替代。已决定不等于已交付，已实现不等于已经验收。
4. 用提交、代码、测试或安装版证据核对现状；日志与代码冲突时记录差异，不能把任一方静默改成另一方。用户意图决定目标，实现与验证决定当前状态。
5. 按下表同步受影响的文档，在日志记录更新位置；不相关文档注明本轮无影响，不为刷新日期重写。
6. 检查遗漏、矛盾、链接和状态，确保后续 session 能从日志追到决定、证据及专题结论。每轮有实质进展即记录，不等发版才补日志。

| 从日志提炼的内容 | 同步位置 |
| --- | --- |
| 用户场景、功能边界、非目标、验收 | PRODUCT；未实现的决定放待办，不放当前能力 |
| 技术决策、模型、数据流、失败与隐私边界 | ARCHITECTURE；分清接受的方案与已运行实现 |
| 交互、视觉与已验证体验 | DESIGN；没有视觉证据不能写已验收 |
| 测试方法、交付门槛、发布与回退步骤 | RELEASE_QA；执行结果留在日志 |
| 客群、收费、权益、运营与商业待决策 | COMMERCIAL；建议不转成对外承诺 |
| 版本、安装、入口与使用说明变化 | 本 README；核对实际产物 |
| 协作与维护规则变化 | 根 AGENTS；不从单次技术偏好生成永久约束 |

逐份分析其他文档时，固定回答六项：**日志中的变化 → 证据与状态 → 原文是否一致 → 保留／更新／归档／待核验 → 修改位置与理由 → 验收方式与未决项**。只检查受影响范围，涉及跨模块或版本回顾时再扩大审查。日志保留过程，专题文档保留当前结论，两者互相引用。
