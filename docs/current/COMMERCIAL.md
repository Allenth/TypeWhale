# TypeWhale Pro 商业化计划

更新：2026-09-05。维护：产品负责人／运营。状态：现有资料收敛与待核验清单，不是新的收费或发布批准。

## 定位与目标用户

围绕高频桌面输入形成使用习惯，优先面向需要口述需求、反馈、邮件和聊天的开发者、产品及办公用户。产品定位与已交付边界以 [PRODUCT](PRODUCT.md) 为准，不主打会议转写或全平台企业系统。

本轮没有市场访谈、销售数据或支付后台证据，因此不填写虚构的用户数、留存或收入。

## 运营执行顺序

以下是收敛后的建议次序，不表示已经招募、收费或对外承诺：

1. 先确认可分发 build 与安装、权限、模型首次准备是否顺畅，得到可复现的首次成功输入流程。
2. 选择一批高频目标用户，记录真实触发场景、阻断点、继续使用意愿与支持成本。历史“20–50 人”是旧建议，不作为已发生人数。
3. 用相同口述素材观察识别、整理和写回分别在哪里失败，避免将 ASR 问题计为提示词问题。
4. 产品负责人确认付费范围、权益、价格与退款机制；历史价格区间和七天退款不自动生效。
5. 按发布门槛完成资料与产物核验，再执行对应规模的推广。对外只描述可证明的能力。

## 指标与数据边界

| 问题 | 建议观察方式 | 本轮数据 |
| --- | --- | --- |
| 首次能否用起来 | 安装 → 权限 → 模型就绪 → 首次写回的完成／失败情况 | 未采集 |
| 是否形成习惯 | 经用户同意的回访与活跃日、成功输入次数 | 未采集 |
| 主流程是否可信 | 用户报告的错误目标、误发、丢内容及恢复情况 | 未汇总 |
| 是否愿意付费 | 经批准的购买流程、实际购买与退款原因 | 未核验 |

不为统计采集口述、截图、剪贴板、Key 或文件路径。初期回访和手工汇总同样需要控制用户内容；不能因为没有 SDK 就假定没有隐私成本。技术边界见 [ARCHITECTURE](ARCHITECTURE.md)。
