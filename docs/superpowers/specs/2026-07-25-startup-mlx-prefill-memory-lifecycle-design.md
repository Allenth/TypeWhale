# Qwen 启动预填与内存生命周期设计

## 目标

Qwen 已安装且被选中时，App 启动后在后台完成模型加载和当前整理提示词预填，使第一次真实整理直接复用 KV 前缀。同时把独立 Worker 的内存计入安全监控。

## 方案选择

- 保持现状：只加载权重。内存最低，但第一次整理仍需计算完整提示词。
- **启动完整预填（采用）**：加载权重后预计算当前整理模式的固定提示词，第一次整理直接命中。
- 首次按键时预填：不增加启动负担，但用户仍承担等待，不采用。

## 行为

1. 仅当本地 Qwen 已选中、模型与运行时就绪、物理内存不少于 16GB 时执行。
2. App 启动稳定后后台预填当前整理模式；不展示、不粘贴、不写入用户历史。
3. 预填只使用固定系统提示词和无用户信息的占位文本，不保存用户正文。
4. 用户在预填开始前发起请求时取消计划；预填已开始时真实请求复用同一串行 Worker，预填结束后立即命中缓存，不重复加载。
5. 切换 DeepSeek、系统睡眠、退出 App 时终止 Worker；唤醒且仍选中 Qwen 时重新预填。
6. 整理模式或提示词变化后按 token 精确匹配，不会错误复用旧缓存。

## 内存治理

- 监控值改为 TypeWhale 主进程 footprint 加 Qwen Worker footprint。
- 现有缓存继续受 4 条、2048 token、384MiB 三重限制。
- 高内存且空闲时终止 Qwen Worker，避免立即重建造成抖动；内存恢复后再后台预热，真实请求仍可按需启动。
- ASR/VAD 的既有高内存 flush + 立即热加载规则保持不变。

## 失败与并发

- 预填失败只记录日志，不影响 App 启动；第一次真实请求走完整 prompt。
- 后台预填只允许一个任务；启动、唤醒、模型切换不会并发创建多个 Worker。
- 用户取消真实生成仍终止 Worker；回到空闲且内存安全后自动恢复预热。

## 验收

- 冷启动日志先出现模型加载和 prompt 预填完成。
- 第一次真实整理 `prompt_cache_hit=true`，实际计算 token 显著少于总 prompt token。
- 16GB 机器使用总 footprint 触发内存安全网；高内存释放后不立即循环重载。
- DeepSeek、睡眠/唤醒、退出、取消和提示词变化路径无回归。
