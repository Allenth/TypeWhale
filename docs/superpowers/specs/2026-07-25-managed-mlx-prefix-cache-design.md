# TypeWhale 本地 MLX 前缀缓存设计

## 背景与目标

TypeWhale 当前通过常驻的 `managed_mlx_llm_worker.py` 直接驱动 Qwen3 4B Instruct。模型已经保持热加载，但每次请求仍会重新计算完整聊天提示词。真实日志显示，短文本整理也会携带约 2200 字符的固定整理说明，热态首 token 通常约 950–1030ms，完整生成约 1.0–1.3s。

本轮目标是在不改变模型、提示词、采样参数和输出语义的前提下，复用连续请求的公共 token 前缀，降低热态首 token 延迟。目标不是通过删减提示词换取速度。

## 范围

### In scope

- 在 TypeWhale 自带的持久化 MLX worker 进程内维护有限容量的内存前缀缓存。
- 复用 `mlx_lm` 已支持的 prompt cache、公共 token 前缀匹配、cache 深拷贝和可裁剪能力。
- 为请求指标增加缓存是否命中、复用 token 数和本次实际预填充 token 数。
- 覆盖智能整理、自动翻译和截图翻译共用的本地 Qwen3 4B 生成链路。
- 缓存异常时安全回退到无缓存生成，不能影响用户得到结果。

### Out of scope

- 不缩短或改写现有提示词。
- 不更换模型、量化格式、MLX 版本或采样策略。
- 不调整 DeepSeek、ASR、粘贴和自动发送倒计时。
- 不把 prompt cache 持久化到磁盘。
- 不在本轮引入并发批处理、投机解码或多个 worker。

### Do not touch

- 用户配置的提示词正文和应用模式规则。
- DeepSeek API 路由与 Keychain。
- 语音模型的热加载及高内存释放策略。

## 推荐架构

worker 在模型加载后创建一个小容量的 `PromptPrefixCache`。每次生成时：

1. 使用现有聊天模板生成完整 prompt token。
2. 以当前模型身份和完整 token 序列查询最近公共前缀。
3. 精确命中或命中较短缓存时，深拷贝缓存并仅提交剩余 token。
4. 命中更长缓存时，仅在 MLX 声明该 cache 可裁剪时深拷贝并裁剪到公共前缀；至少保留一个未处理 token，满足生成接口边界。
5. 无安全命中时创建新的空 prompt cache，按现有路径处理全部 token。
6. 生成完成后，将“完整输入 prompt token + 本次生成 token”及最终 cache 放入小容量 LRU。

该行为采用当前安装版 `mlx_lm.server.LRUPromptCache` 的同类语义，但 TypeWhale 只实现单进程、串行请求所需的最小边界，避免引入 HTTP server 或批处理依赖。

## 缓存生命周期与隐私

- 缓存仅存在于 worker 内存，App 退出或 worker 重启即清空。
- 缓存容量固定且较小，超过容量按 LRU 淘汰。
- 模型目录变化或模型重新加载时全部清空。
- 缓存不落盘、不跨用户、不进入日志；日志只记录 token 数量和命中状态。
- 不记录或输出 prompt、用户原文、KV 内容。

## 正确性与回退

- 缓存命中不能改变传给模型的完整 token 序列。
- 每个请求使用缓存的独立副本，生成过程不得污染仍存储在 LRU 中的条目。
- 如果 cache 不可裁剪、公共前缀不足、深拷贝失败或 MLX cache API 异常，本次请求使用空 cache 重新执行。
- 缓存优化失败不能触发第二次用户可见生成，也不能让请求重复粘贴。
- 现有 worker 错误协议保持不变。

## 指标

在 worker 响应 metrics 中增加：

- `prompt_cache_hit`: 是否复用了至少一个 prompt token。
- `prompt_cache_reused_tokens`: 复用 token 数。
- `prompt_tokens_evaluated`: 本次真正送入模型预填充的 token 数。

Swift 协议层解码这些字段，并在 `managed_mlx request_done` 中记录。现有字段保持兼容，老 worker 未返回新字段时按未命中处理。

## 测试策略

### 自动化

- 首次请求未命中并写入缓存。
- 相同固定前缀、不同用户文本的第二次请求命中，且只处理剩余 token。
- 提示词模式变化时只复用真实公共前缀，不串用后续 token。
- 模型变化时缓存清空。
- 缓存对象使用独立副本，连续请求不会污染历史条目。
- 不可裁剪或缓存异常时回退到完整 prompt。
- 协议层可解码新 metrics，也兼容缺少新字段的旧响应。

### 隔离性能验证

使用正式 Qwen3 4B 模型和正式 worker，在同一进程连续发送语义相近但用户文本不同的请求。记录：

- 首轮冷缓存 TTFT；
- 后续热缓存 TTFT；
- 复用 token 数；
- 输出是否非空并符合整理要求。

性能实验只作为是否启用优化的门禁，不用硬编码机器相关的绝对测试阈值。

### 安装版验收

在 `/Applications/TypeWhale Pro.app` 中连续完成至少三次短语音整理：

- 第一次结果正确；
- 第二、三次日志显示 `prompt_cache_hit=true`；
- 热态 TTFT 相比当前约 1 秒有明显下降；
- 输出质量、粘贴、取消和自动发送行为不变；
- 模式切换及截图翻译不会复用错误上下文。

## 成功与失败标准

成功：在输出一致性测试通过的前提下，安装版连续请求稳定命中缓存，热态 TTFT 明显下降，且无新增崩溃、串文或重复输出。

失败：缓存命中不能稳定降低 TTFT、输出与无缓存基线不一致、出现上下文串用，或需要修改提示词语义才能获得收益。发生任一失败时不启用该优化，并保留现有无缓存链路。
