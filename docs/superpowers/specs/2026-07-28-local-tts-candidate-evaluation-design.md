# TypeWhale 本地朗读候选接入、体验评测与淘汰设计

## 1. 目标

TypeWhale 当前已管理 8 款本地 TTS 候选，但只有 Sherpa VITS Melo 与
ZipVoice 已经稳定接通朗读实验室。其余候选处于权重已下载、运行时未接通或
资格验证失败状态，不能把“已下载”误写成“可播放”。

本阶段的目标是建立真实、公平、可重复的本地试听环境：

1. 让 8 款候选都能在“声音 → 朗读测试”中实际生成和播放音频；
2. 先比较真实听感，再比较资源利用率，最后寻找体验与工程成本的平衡；
3. 形成可追溯的冷启动、热启动、首音、RTF、内存和稳定性数据；
4. 最终只保留 1–2 款综合表现最好的模型；
5. 淘汰后删除落选模型、专属运行时、缓存、临时文件和旧源副本，不留残留。

## 2. 产品原则

### 2.1 评判顺序

候选淘汰必须按以下顺序进行，不能提前用部署便利性替代用户体验判断：

1. **体验门禁**：自然度、清晰度、中英文发音、长文本稳定性、机械感、
   漏字、重复、异常静音和爆音；
2. **资源门禁**：首音时间、冷/热启动时间、RTF、峰值内存、持续内存和
   长文本资源增长；
3. **工程门禁**：是否需要 Python、Conda、Homebrew，运行时大小、依赖
   复杂度、许可证和后续维护成本；
4. **综合平衡**：只在体验合格者之间综合速度、资源和部署纯净度决定最终
   保留项。

性能接近时，完全不依赖 Python、Conda、Homebrew 的 Core ML、MLX、
ONNX Runtime、C/C++ 或 Rust 路径优先。

### 2.2 测试阶段与正式阶段分离

- 当前所有候选、运行时和评测数据均属于实验资产，不代表正式产品承诺。
- 测试阶段允许使用 TypeWhale 管理的隔离 Python 环境建立官方实现基线。
- 隔离环境不得污染系统 Python，不得要求用户安装 Conda、Homebrew 或
  手工启动服务。
- 最终入选模型必须重新审视零配置交付路径；不能把实验依赖原样视为正式
  发布方案。
- Reader Demo、OpenClaw 当前稳定声音链路和正式内容朗读链路不参与本轮
  路由切换。

## 3. 范围

### 3.1 In scope

- Sherpa VITS Melo 中英；
- ZipVoice Distill INT8 中英；
- Kokoro INT8 多语言；
- Qwen3-TTS 0.6B Core ML；
- Qwen3-TTS 1.7B Core ML；
- Fun-CosyVoice3 0.5B；
- MOSS-TTS Local Transformer v1.5；
- VoxCPM2；
- 各候选离线运行时、播放适配、取消、错误状态和性能采集；
- 统一试听文本、盲听标识、结果存储和最终清理清单。

### 3.2 Out of scope

- 当前阶段直接决定正式产品默认模型；
- 把所有候选接入 OpenClaw 或 Reader Demo；
- 为落选模型建设长期生产维护能力；
- 云端 TTS、在线 API 或联网推理后备；
- 声音克隆、训练、微调和自定义音色编辑器；
- 在评测完成前删除任一候选权重。

### 3.3 Do not touch

- Reader Demo 已有引用、模型和行为；
- OpenClaw 当前 Sherpa/Melo 稳定链路；
- ASR、VAD、智能整理和语音粘贴链路；
- 其他 session 的未提交文件和构建现场；
- 未经最终淘汰批准的模型、运行时和缓存。

## 4. 技术策略

采用“原生优先、实验隔离兜底”的多运行时架构。评测层使用统一协议，不要求
所有模型共享同一个推理框架。

### 4.1 运行时选择

| 候选 | 第一验证路径 | 备用/交叉验证路径 | 当前角色 |
| --- | --- | --- | --- |
| Sherpa VITS Melo | sherpa-onnx | 无 | 已验证基准 |
| ZipVoice | sherpa-onnx | 无 | 已验证基准 |
| Kokoro | sherpa-onnx | MLX 或独立 ONNX 路径 | 定位 NaN 并交叉验证 |
| Qwen3-TTS 0.6B | 已下载 TTSKit Core ML | 仅在 Core ML 不可用时评估 MLX/C | 原生优先候选 |
| Qwen3-TTS 1.7B | 已下载 TTSKit Core ML | 仅在 Core ML 不可用时评估 MLX/C | 高质量原生候选 |
| Fun-CosyVoice3 | 官方隔离运行时 | Candle/Rust 仅作后续原生化评估 | 官方音质基线 |
| MOSS-TTS | 官方 llama.cpp + ONNX 路径优先 | 官方隔离 Python 路径 | torch-free 优先候选 |
| VoxCPM2 | 官方隔离运行时 | 有成熟原生路径后再交叉验证 | 高质量高资源候选 |

非官方运行时不能在未经官方实现音质对照的情况下成为唯一评测结果。

### 4.2 统一 Worker 协议

每个运行时适配器必须实现同一组能力：

- `health`：报告运行时、模型和必需文件是否就绪；
- `prepare`：加载模型并返回冷/热状态与准备耗时；
- `synthesize`：接收纯文本和输出路径，生成本地 WAV；
- `cancel`：停止当前生成并清理临时输出；
- `shutdown`：退出专属 worker；
- 结构化返回首音、合成耗时、音频时长、采样率、RTF 和错误类型。

模型内部 API 差异只能存在于适配器内，UI 和评测服务不得按模型名称堆叠
分支。

### 4.3 进程与内存隔离

- 一次只运行一个候选，避免大模型互相争抢统一内存；
- 切换模型时先取消并退出前一个实验 worker；
- 记录主 App 与 worker 的总峰值内存；
- 长时间运行后检查内存是否持续增长；
- 取消或失败时删除未完成 WAV；
- 测试 worker 不得成为登录后常驻服务；
- 正式链路的热加载和高内存释放规则保持不变。

## 5. Kokoro NaN 调查

Kokoro 不能简单标记为“模型坏了”。必须复现并记录第 9 次失败的完整边界：

- 固定输入文本、音色 ID、语速、线程数和量化模型；
- 每轮检查返回样本是否包含 NaN、Inf、全静音或异常峰值；
- 区分模型加载后状态污染、特定文本、特定音色、INT8 量化和
  sherpa-onnx 版本问题；
- 使用另一条离线实现和相同权重/等价权重交叉验证；
- 只有明确定位后才能决定修复、换运行时或淘汰。

若备用实现稳定而 sherpa-onnx 不稳定，资格结论应归因于运行时组合，不应
直接归因于 Kokoro 模型家族。

## 6. 统一体验测试

### 6.1 固定文本集

每款候选使用相同的四类文本：

1. 中文短句：自然语气、数字、日期和常见标点；
2. 英文短句：日常英语与技术词；
3. 中英混合：TypeWhale、ChatGPT、GitHub、Core ML 等真实产品内容；
4. 中文长段落：多句、停顿、数字和专有名词，检查漏字、重复和后段退化。

模型不支持某语言时必须明确标注能力缺失，不能用失败结果冒充音质得分。

### 6.2 盲听

- 生成文件使用随机样本编号，不在试听时显示模型名称；
- 同一文本、同一音量归一化规则、尽可能接近的音色条件；
- 分别记录自然度、清晰度、中文发音、英文发音、长文本稳定性；
- 保留主观备注，例如机械感、情绪过强、停顿不自然、数字错误；
- 盲听评分与性能数据分开呈现，避免速度影响听感判断。

### 6.3 性能与稳定性

每款至少完成：

- 1 次冷启动；
- 3 次连续热启动；
- 3 次相同短句复跑；
- 1 次长段落；
- 1 次生成中取消；
- 1 次切换到其他模型再切回；
- 断网复跑。

自动检查：

- WAV 可解码且时长大于零；
- 样本不含 NaN 或 Inf；
- 非全静音；
- 峰值不过载；
- 没有异常重复增长；
- 失败后 App 和下一款模型仍可继续测试。

## 7. 朗读实验室状态设计

模型状态必须区分：

- `权重已下载`；
- `运行时准备中`；
- `可测试`；
- `测试失败`；
- `资格通过`；
- `已淘汰`。

只有 `可测试` 或 `资格通过` 的候选允许播放。失败状态显示可执行的错误摘要，
但不在 UI 中暴露本机绝对路径。下载完成不得自动等同于可播放。

播放结果继续显示冷/热启动、首音、生成时间、音频时长、RTF 和峰值内存。
体验评分不自动替用户决定，保留人工盲听入口。

## 8. 结果数据与隐私

- 结果只保存在本机；
- 性能记录不保存用户自由输入的原文；
- 固定评测文本只记录样本 ID；
- 临时音频集中放入 TypeWhale 实验目录；
- 每个结果绑定模型 ID、权重摘要、运行时版本和配置摘要；
- 更新运行时或权重后必须重新取得资格，不能沿用旧结果。

## 9. 淘汰与清理门禁

评测阶段不删除候选。最终选择 1–2 款后，清理必须分两步。

### 9.1 删除前审计

输出并由产品负责人确认：

- 保留模型及其运行时；
- 淘汰模型的精确目录；
- 每个目录占用空间；
- 专属虚拟环境、编译产物和下载缓存；
- 临时 WAV、评测输出和旧源副本；
- 是否存在多个相同哈希的重复权重；
- 是否被 Reader Demo、OpenClaw 或其他功能引用。

### 9.2 删除后验证

- 优先移动到废纸篓，除非用户明确批准永久删除；
- 重新扫描 TypeWhale、旧实验目录和常见模型缓存；
- 检查已淘汰模型名称、权重和运行时是否仍有残留；
- 断网复测保留的 1–2 款；
- 构建并验证安装版不再引用落选资源；
- 报告实际释放空间和仍保留的共享依赖。

任何共享运行时只有在没有其他功能引用时才能删除。

## 10. 验收标准

本阶段完成需同时满足：

1. 8 款候选均得到真实运行结论：可播放、明确失败或明确不支持某语言；
2. 可播放候选能从安装版朗读实验室生成并播放输入文字；
3. 每款完成统一文本、冷/热、取消、长文本和断网测试；
4. 指标来自真实运行，不使用占位实现或伪造数据；
5. Kokoro NaN 有可复现根因或跨运行时对照结论；
6. 盲听结果与性能结果分离呈现；
7. Reader Demo、OpenClaw 和现有两款基准模型没有退化；
8. 最终保留项由产品负责人根据体验优先原则决定；
9. 删除前提供精确清单并再次获得批准；
10. 删除后完成残留扫描、空间核对和保留模型断网复测。

## 11. 实施顺序

1. 固化统一协议、状态模型和评测文本；
2. 复核现有 Sherpa 与 ZipVoice 基线；
3. 修复或替换 Kokoro 运行时；
4. 接通两档 Qwen3-TTS Core ML；
5. 接通 MOSS-TTS 的 torch-free 路径；
6. 为 CosyVoice3 和 VoxCPM2 建立官方隔离运行时基线；
7. 完成全部体验与性能测试；
8. 由产品负责人盲听并决定最终保留 1–2 款；
9. 输出删除审计，获得明确批准后清理；
10. 收敛胜出者的正式零配置交付方案。
