## 当前目标

重新设计 TypeWhale 的实时预览与增量转录代码，使它能够统一支持：

1. 非流式模型的预览，例如当前 SenseVoice 周期性识别音频快照。
2. 本地流式模型的预览。
3. 在线流式模型的预览。

长期目标包括连续录制数小时、增量生成可靠转录、停止时不必重新识别整段录音，同时保留普通短口述已经验证的 final ASR 与粘贴体验。

目标交付形态进一步提升为可复用的语音转文字 SDK：核心转录能力以独立代码包提供，预览窗作为可选子模块订阅统一事件。TypeWhale 是首个宿主，但接口不能只服务当前胶囊；未来所有需要展示流式传输、实时字幕或增量文本的界面都应复用同一能力。

## 历史沟通与架构演进

### 2026-06-13：建立 1.2 预览体验的代码基础

来源：`docs/开发日志.md` 中“录音胶囊即时反馈优化”“预览层文本缓存抽象”“停顿自动完成功能”等记录。

- 用户体验目标：按下快捷键后必须立刻得到“正在录音”的确定反馈，不能等待 AVAudioEngine 完成启动才显示胶囊。
- 代码边界决定：从 `RecordingCapsuleView` 中抽出 `CapsuleTextBuffer`，由它管理 `targetDraft`、`displayedDraft`、首帧门槛、原位刷新和逐步推进；View 继续负责绘制、裁切和动画 timer。
- 当时的数据模型：SenseVoice 对本轮录音的累计音频做周期性快照识别，胶囊显示最新累计结果。
- 当时的自动结束方案：依赖“实时预览文本是否变化”刷新停顿 timer；final 仍然识别完整录音，不使用预览文本作为最终输入。
- 后续结论：`CapsuleTextBuffer` 的算法与“累计快照”输入语义一起构成了 1.2 的好体验，不能脱离数据源单独评价。
- 当前有效性：即时反馈、final 与 preview 分离仍有效；用 preview 文本驱动自动结束的做法已被后续 Silero 状态机取代。

### 2026-06-14：用 Silero 限制静音快照进入预览 ASR

来源：`docs/开发日志.md` 中“改用 Silero VAD 处理静音误识别”。

- 用户反馈：只给 final ASR 加 VAD 并没有改善胶囊，静音和环境噪声仍会在实时预览中吐出 `The.`、`我。` 等文本。
- 修正：每个 realtime snapshot 先经过 Silero；没有检测到人声时删除快照，不进入 realtime ASR，也不更新胶囊。
- 设计含义：final VAD 与 preview VAD 是不同入口，修好 final 不等于修好预览。
- 当前有效性：Silero 仍是人声判断基础，但 2026-06-29 起预览显示不再被实时 VAD 硬门控；VAD 主要负责自动结束和分块边界。

### 2026-06-15：首字延迟、宽度稳定与模型预热

来源：`docs/开发日志.md` 中“降低胶囊首次实时预览延迟”“修复胶囊慢速说话时宽度抽动”。

- 用户反馈：开始说话后首段文字出现太慢；慢速口述时，ASR 修正文本会让胶囊宽度反复收缩和扩张。
- 调整：首个快照提前到约 `0.30s`，后续约 `0.50s`；首段门槛从 8 字降为 3 字；启动时预热 SenseVoice recognizer。
- 显示稳定策略：单次录音内宽度只增不减，草稿重置为空时才恢复紧凑尺寸。
- 保留边界：final 继续使用完整录音；当时仍保留 realtime VAD，避免以低延迟换取静音吐字。
- 当前有效性：首反馈优先、模型预热、单轮宽度保持仍是有效体验原则；具体快照节奏属于非流式引擎策略，不应写死到统一上层协议。

### 2026-06-25：预览噪声过滤与非流式快照局限暴露

来源：`docs/开发日志.md` 中“识别准确率排查与实时预览稳态优化”“1.3.36 收紧胶囊实时预览噪声过滤”。

- 用户反馈：静音、停顿和半句话快照会冒出随机单字、短英文碎片和密集标点。
- 排查结论：线程数不是文本退化根因；主要问题是非流式 SenseVoice 对过早、过短快照的补全与幻觉。
- 决定：预览使用独立的 `isMeaningfulRealtimePreviewText`，拒绝单字、纯标点变化、短子串回退和疑似英文碎片；final 使用另一套规则。
- 当前有效性：预览过滤和最终过滤必须分离仍有效；这些有损过滤说明 preview 文本不能未经新权威状态层处理就直接成为最终转录。

### 2026-06-25：第一次分段方案及其失败

来源：`docs/开发日志.md` 中“1.3.40 实时预览分段重构”“1.4.21 胶囊实时预览稳定性修复”。

- 原始问题：20 秒滑动窗口不断右移，窗口头部可能切在半个音节；SenseVoice 每次返回的整段文本随窗口移动而变化，`CapsuleTextBuffer` 又按位置刷新，最终出现新旧字符混杂和乱码。
- 第一版方案：引入 `committedPreviewText + 当前短段`；停顿约 `0.7s` 或连续说话约 `16s` 时提交，并立即 `resetRealtimeWindow()`。
- 用户反馈：自然换气、思考和稍长静音都会导致预览重置、上下文断裂和明显乱跳，体验比 1.2 更差。
- 临时修正：把停顿提交放宽到 `3.0s`、窗口扩到 `45s`，并让非前缀文本干净替换。
- 失败结论：问题不只是阈值太短，而是把自然停顿同时当作“语义提交”和“音频窗口清零”边界。
- 当前有效性：这条“短停顿即 reset / sliding window”路线明确失败，不得恢复。

### 2026-06-25：回到 1.2 累计快照与动效基线

来源：`docs/开发日志.md` 中“1.4.22 胶囊预览恢复累计上下文策略”至“1.4.30 清除实时预览分段残留”，以及 `DESIGN.md`。

- 用户核心观点：胶囊必须让人清楚看到自己正在说什么；不能因为当前不是 streaming ASR，就降低产品目标。1.2 已证明存在更好的体验。
- 回退过程：取消自然停顿触发的 segment commit 和窗口 reset，恢复从录音开始累计的快照；随后恢复 1.2 的局部淡入、75ms 尾部推进和按当前显示长度刷新。
- 动效分歧：
  - 立即干净替换解决混字，但文字跳变生硬。
  - 整段淡入解决硬切，却让整段闪烁。
  - 纯逐字从一个字开始又让用户误以为内容丢失。
  - 最终回到 1.2：首段局部淡入，已显示长度内刷新，新增尾部平滑推进。
- 1.4.30 决定：删除当时的 `committedPreviewText`、generation、segment commit 和 reset-window 残留，避免错误路线继续误导后续实现。
- 当前有效性：1.2 仍是动效和确定感基线；“累计整段快照”后来因性能被取代，因此 `DESIGN.md` 把它描述为当前架构已经过时，需要在正式新方案中修正。

### 2026-06-25：模拟流式展示提议，未进入生产

来源：`docs/开发日志.md` 中“模拟流式传输实现思路与策略复盘（待实现）”。

- 提议对象：final ASR 之后等待智能整理结果的 UI 反馈，不是录音阶段 ASR streaming。
- 方案：用 UI-only presenter 按字符或短句逐步展示占位/原文，真实整理结果返回后覆盖；模拟内容不得进入粘贴、历史或计费。
- 当前有效性：标记为待实现的历史提议，不能作为当前预览能力。它留下的有效原则是“视觉上的渐进内容不能冒充权威最终文本”。

### 2026-06-26：预览卡死保护与 timer 职责拆分

来源：`docs/开发日志.md` 中“1.4.39 拆分后台/录音/胶囊 timer”“1.4.47 修复胶囊实时预览偶发卡死保护”。

- 用户反馈一：能耗治理后胶囊动画消失。根因不是 View，而是后台健康、录音安全和胶囊刷新共用 timer，后台降频连带破坏用户可见节奏。
- 决定：拆分 `backgroundHealthTimer`、`recordingSafetyTimer`、`capsuleStatusTimer`；文字动画继续由 View 自己管理。
- 用户反馈二：胶囊偶尔停止吐字，但 final 和整理正常。根因是 realtime callback 慢或丢失后 `realtimeBusy` 永久占用。
- 决定：加入 snapshot ID、超时、stale callback 保护、latest-only pending 和诊断日志。
- 后续复盘：超时只释放上层 busy，并不取消共享原生 ASR 队列中的底层工作；这正是当前新架构必须修复的调度语义。
- 当前有效性：timer 按职责拆分、任务代次和 stale callback 保护仍有效；“超时即继续放行下一请求”不能原样迁移。

### 2026-06-27：累计快照的长录音性能上限与错误收口

来源：`docs/开发日志.md` 中“1.4.49 跨录音轮次不吐字”“1.4.51 长录音后段胶囊快照卡住”“1.4.52 将单段录音上限收回 45 秒”。

- 跨轮次问题：上一轮 stale callback 清掉 active snapshot id，却没有重置 `realtimeBusy`，导致第二轮快照永远只进入 pending。结论是 realtime 状态必须以 session/task 为边界完整重置。
- 长录音问题：累计快照每 0.5 秒重写从开头到当前的全部音频，成本随时长增长，后段会卡在快照生产或 ASR；这是非流式累计方案的结构性 O(n²) 问题。
- 错误收口：一度把 45 秒后的退化解释成 SenseVoice 单段硬上限，并把录音限制收回 45 秒。
- 用户反证：1.2 曾稳定识别一两分钟，45 秒上限不是成立根因；该限制在后续版本撤回。
- 有效结论：真正的长语音方向是“有边界的音频块 + 增量识别 + 文本合并 + 连续展示”，不是无限累计快照，也不是用时长上限掩盖架构问题。

### 2026-06-29：当前块提交路线建立

来源：`docs/开发日志.md` 中“人声门控重构（Silero）、删除能量 VAD、实时预览分块提交”和当前 `docs/ARCHITECTURE.md`。

- 背景：每 0.5 秒重复识别整段增长音频导致 O(n²) 成本；长录音必然变慢、发热和跳变。
- 新方案：只重复识别当前块；块达到约 10 秒后等待 Silero 停顿提交，一直不停顿则约 18 秒硬提交；已提交前缀冻结，块 final snapshot 进入专用队列。
- 与失败方案的差异：不再“遇到短停顿就重置全部显示”；切块是有最小时长的资源边界，已提交前缀持续保留。
- 当时明确局限：块边界仍是朴素字符串拼接，没有重叠去重、静音裁剪和真正的 streaming decoder。
- 当时的模型取舍：用户主动放弃“把实时预览换成流式 transducer”的 B 方案，主要阻碍是候选中文模型训练数据许可证，不是技术不可实现。这个决定针对当时候选模型，不应被解释为永久放弃本地流式预览。
- 当前有效性：这是当前 SenseVoice 非流式预览的基础；但其状态归约和调度仍困在 `SpeechInputCoordinator`，正是本次迁移要替换的部分。

### 2026-06-29：失败门控实验与实时证据的产品含义

来源：`docs/开发日志.md` 中“1.5.58 移除 VAD 门控实验”“1.5.61 修复实时预览有字但最终识别被 VAD 当空录音”。

- 波形/VAD 实验：把 Silero 两档状态接入波形后，用户确认体验几乎不可用，最终退回 1.4 已验证折线；说明识别门控信号不应顺手控制视觉表现。
- final VAD 冲突：胶囊已经显示有效文本，但 final VAD 仍可能返回 `no_speech` 并跳过最终识别。
- 修正：预览有意义文本或实时 VAD 命中过人声时，final VAD 从硬闸门降为软闸门，继续运行 final ASR。
- 有效原则：用户已经看到的有效预览是产品证据，不能被后续单一检测器静默否定；但它仍不是可以直接粘贴的最终文本。

### 2026-06-30：Presenter 抽象、主题分化与架构文档收口

来源：`docs/开发日志.md` 中“1.5.70 实时预览主题切换 + 预览能力抽象”“架构文档合并为单一当前入口”“架构重构前代码 Review 行动项补充”。

- 用户要求：把预览窗全部功能从具体 UI 中剥离，再支持默认胶囊与刘海主题。
- 实现：引入 `PreviewPresenting`，`RecordingPanel` 和 `NotchPreviewPresenter` 各自实现，协调器继续用命令式方法驱动。
- 后续暴露的问题：协议存在默认 no-op，两个 Presenter 对 `draft=nil` 和隐藏生命周期的语义不完全一致；说明抽出了类型，却没有抽出统一 ViewState 和状态契约。
- 文档治理决定：`docs/ARCHITECTURE.md` 成为唯一当前架构入口；旧 ADR、旧 preview design 降级为历史。
- Review blocker：`AudioRecorder` 在块最终快照写入成功前就推进 chunk 并清空缓冲，写入失败可能破坏“final snapshot 不丢失”不变量；`SpeechInputCoordinator` 仍是主要职责集中点。
- 当前有效性：Presenter 可替换方向正确；新迁移应从命令式协议升级为统一 `PreviewViewState`，并把块提交事务放到可测试状态机中。

### 2026-07-10：自动结束与预览正式解耦

来源：`docs/VAD_AND_WAVEFORM_DESIGN.md` 和 `docs/开发日志.md` 中 1.9.36–1.9.37 记录。

- 当前策略：Silero probe 携带 `taskID`，使用容量 4 的有界 FIFO；两次连续 `no_speech` 才允许结束，队列仍有更新音频时必须延期决定，溢出则安全停用本轮自动完成。
- 重要边界：实时预览开关和停顿自动完成开关彼此独立；VAD 失败只关闭自动完成，不关闭手动结束和硬上限。
- 架构启示：VAD 状态机已经证明“纯策略对象 + 明确事件 + 有界队列 + 安全降级”适合这类异步语音流程；新的预览 Reducer 和 Scheduler 应采用相同模式，而不是继续增加协调器布尔量。
- 当前有效性：全部有效，是本次新预览架构可直接借鉴的本地成功模式。

## 从历史记录提炼的稳定约束

1. 胶囊是用户的确定性锚点，首个可见反馈优先，但不能用未经确认的视觉文本冒充最终结果。
2. final 与 preview 必须在产品语义上解耦；preview 故障不能阻塞 final，final 检测器也不能无视已经出现的有效实时证据。
3. 非流式 SenseVoice 不能无限重复识别从录音开头累计增长的音频；数小时录音必须使用有界块和增量持久化。
4. 禁止恢复“短自然停顿即清空窗口/重置显示”的失败路线；分块必须是资源和事务边界，不是随意的视觉 reset。
5. `CapsuleTextBuffer` 只能负责显示动画，不能决定权威 transcript 中哪些字符继续存在。
6. 预览专用幻觉过滤是有损的，不能未经分层直接作为最终文本规则。
7. timeout、cancel、stale 和 failed 必须是不同事件；上层超时不能伪装成底层任务已经取消。
8. 每次录音、每个 chunk、每次 revision 都必须有稳定身份，跨轮次状态必须完整清理。
9. 本地非流式、本地流式、在线流式应共享上层事件和状态模型，但允许各引擎拥有不同的采样、分块、重连和延迟策略。
10. 新架构必须旁路验证后逐段接管，不能再次用一次性重写赌历史好体验。

## 2026-07-10 沟通时间线

### 1. 讨论对象从界面设计校正为代码设计

- 用户观点：要检查的是预览胶囊的代码设计，不是视觉界面。
- Agent 初始理解偏差：最初按 UI / 交互设计复核进入。
- 修正：停止视觉审查，改为检查调用链、状态机、并发调度、模块职责和历史架构演进。
- 结论：后续“预览设计”默认指代码与系统架构，除非明确讨论 UI。

### 2. 当前实现的问题是混合架构，而不是单个参数

- Agent 判断：当前实现叠加了两代稳定机制。
  - Application 层使用 `committedPreviewText + latestPreviewText` 表示冻结前缀和可变尾巴。
  - Presentation 层的 `CapsuleTextBuffer` 再次决定哪些字符保留、缩短或逐字显示。
- 历史依据：`CapsuleTextBuffer` 延续 1.2 累计快照时期的显示算法；当前底层已重新采用 10–18 秒分块冻结。
- 风险判断：两层同时拥有“文本真相”，可能造成残留尾字、状态不一致和难以测试的修补逻辑。

### 3. 对协调器问题优先级的观点调整

- 初始 Agent 分级：`SpeechInputCoordinator` 承担过多职责列为 P1。
- 用户问题：是否需要提升优先级。
- 调整后的共识：
  - “预览调度和状态归约必须从协调器中迁出”提升为 P0 架构阻断项。
  - “全面拆分整个协调器”仍为 P1，不能借预览迁移发动高风险的大爆炸式重写。
- 原因：realtime 超时、final 优先级、块提交、乱序和 Presenter 更新全部困在协调器私有状态中，已经直接影响正确性和可测试性。

### 4. 关于直接把当前预览作为最终输出的分歧

- 用户方向：考虑直接使用预览代码产生最终输出，以支持连续录制数小时。
- Agent 反对的部分：不能直接把当前胶囊的 `displayedDraft` 或当前 preview 文本当作最终结果。
- 原因：
  - `CapsuleTextBuffer` 包含为了视觉稳定而保留旧字符的策略。
  - 预览过滤会丢弃部分短词和疑似幻觉，规则不适合作为最终转录规则。
  - 当前分块只是字符串拼接，缺少边界合并、持久化、崩溃恢复和完整的超时语义。
- Agent 推荐的重新表述：建立权威的增量转录主链路；胶囊和最终输出都读取这条主链路，胶囊只是实时投影。
- 尚未最终确认：普通短口述是否长期保留完整录音 final ASR，还是未来也切换到权威增量转录。

### 5. 关于“重构”与“迁移”的观点统一

- 用户观点：不在原代码上重构；重新建立文件和合理架构，再把旧代码逐步迁移过去。
- Agent 判断：方向正确，应采用 Strangler Migration（旁路建立、逐段接管、最后删除旧实现）。
- Agent 的建设性反对：不能只建立另一个新的巨型文件，否则只是复制当前协调器问题。
- 推荐结构：建立 `Application/RealtimeTranscription/` 模块，由一个 Facade 作为入口，内部拆分调度、Reducer、状态、Segment 和 ViewState 映射。
- 迁移原则：
  1. 新链路先旁路运行，不改变用户行为。
  2. 与旧链路记录差异。
  3. 验证后先接管预览状态。
  4. 再接管分块和 ASR 调度。
  5. 最后决定是否接管长录音最终结果。
  6. 删除旧变量、旧方法和失效文档。

### 6. 三类预览能力的划分

- 用户提出三层功能：
  1. 非流式输出模型预览，当前代表是 SenseVoice。
  2. 流式输出模型预览，当前理解为本地流式模型。
  3. 在线流式输出模型预览。
- Agent 架构解读：三者应是三种可替换的 `PreviewTranscriptionEngine` 策略，而不是三套胶囊代码。
- 推荐统一事件模型：
  - `partial(segmentID, revision, text)`
  - `finalized(segmentID, text, timeRange)`
  - `reset(segmentID)`
  - `failed(error, recoverability)`
  - `completed`
- 推荐运行规则：单次会话只有一个主引擎；允许明确的故障切换，不默认同时运行三套引擎。
- 用户决定：同意“单会话只激活一个主引擎，允许故障后切换备用引擎”。三种引擎不默认并行，也不通过竞争输出决定文本真相。

### 8. 确认单主引擎与故障切换原则

- 用户决定：单会话只激活一个主引擎，允许故障后切换备用引擎。
- 权威性：任一时刻只有当前 active engine 可以产生新的权威转录事件；备用引擎未接管前不得并行改写 transcript。
- 资源含义：默认不同时运行三套识别，避免重复 CPU/GPU/内存、在线费用和结果竞争。
- 后续必须设计：触发切换的错误分类、切换优先级、未确认 partial 的处理、已 finalized segment 的保留、引擎来源记录与防抖/熔断。

### 9. 将目标提升为可复用语音转文字 SDK

- 用户一句话结论：将相关能力抽象为 SDK，最低要求也是独立代码端，以便未来在多处展示流式传输的场景中复用；进一步可以把语音转文字整体做成 SDK，并把预览窗作为子模块。
- Agent 判断：方向成立，而且比“只迁移胶囊预览代码”更能形成稳定边界。
- 核心边界：
  - 转录 Core 不依赖 AppKit、胶囊或主窗口。
  - Preview UI 是可选模块，只订阅统一 `TranscriptionEvent` / `TranscriptState`。
  - 非流式 SenseVoice、本地流式模型、在线流式服务是 provider adapter，不向上暴露各自特殊状态。
  - 音频采集、持久化、故障切换和 UI 展示可分别替换，不能打包成一个新的巨型类。
- 推荐交付方式：先在当前仓库建立 SDK-quality 的本地 Swift Package，用真实 TypeWhale 迁移验证接口；边界稳定后再决定是否拆成独立仓库或公开二进制 SDK。
- 价值：同一能力可服务默认胶囊、刘海预览、主窗口实时文本、长录音转录、字幕层、在线流式回复和未来其他宿主。
- 风险：如果“包含预览窗”被理解成 Core SDK 强依赖 AppKit，SDK 会失去跨界面和跨平台复用价值；必须保持 Core 与 UI 扩展分层。

### 10. 将多线程与多访问场景列为 SDK P0 契约

- 用户要求：进一步讨论多线程问题，因为 SDK 可能被多处同时访问或交替访问。
- 本地基线：当前开发环境为 Swift 6.2.4；现有 `SpeechInputCoordinator` 依赖 `@MainActor`，`AudioRecorder` 和 `NativeSenseVoiceBridge` 则混用 DispatchQueue、锁与 `@unchecked Sendable`，不能原样作为公共 SDK 线程契约。
- 官方并发模型依据：
  - `Sendable` 用于表达可安全跨并发域传递的值；可变共享状态必须由 actor、锁或不可变值保护。
  - actor 提供隔离和串行状态访问，但默认 actor 共享全局并发线程池，不等价于“每个 actor 固定占一条线程”。
  - `AsyncStream` 适合把 callback API 转为异步序列，但同一个 iterator 不能被多个并发调用者竞争 `next()`；SDK 若需要多个界面同时观察，必须提供真正的多订阅广播，每个 subscriber 拿独立 stream。
- 建议的并发分层：
  1. `TranscriptionSDK` 是 `Sendable` 门面，可以从不同 Task 安全调用，不暴露内部队列。
  2. 每个 `TranscriptionSession` 由独立 actor 隔离，`start/append/finish/cancel/switchProvider` 在该 session 内严格有序。
  3. `TranscriptEvent`、`TranscriptSegment`、配置和错误全部设计成不可变 `Sendable` 值。
  4. Session 内事件带单调递增 `sequence`；保证单 session 总顺序，不承诺不同 session 的全局顺序。
  5. 多个 UI/业务消费者通过 broadcaster 获取独立 `AsyncStream`，慢消费者不能阻塞识别状态机；每个订阅者必须有明确 buffer 和丢弃策略。
  6. 每个 Provider 自己声明并发能力：串行、有限并行或可并行；统一由 provider admission controller 执行，不由调用方猜测模型是否线程安全。
  7. 本地重模型默认使用有界执行槽；同模型非线程安全 recognizer 不允许被多个 session 并发调用。
  8. 音频实时 callback 只做有界复制/入队，不 `await` actor、不做识别、不做磁盘重活。
  9. transcript 状态、音频 I/O、持久化和 UI 分属不同隔离域；Preview UI 统一在 `@MainActor` 消费 ViewState。
  10. `finish`、`cancel`、provider fallback 和崩溃恢复必须幂等；晚到 callback 通过 `sessionID + providerEpoch + sequence` 丢弃。
- 尚未决定：第一阶段是否允许同一进程同时存在多个 active transcription session；即使允许，物理麦克风、本地模型、在线连接和文件转录也需要不同资源政策。
- 参考：Apple `Sendable`、`Actor`、`AsyncStream` 文档，以及 Swift 6 concurrency/library-evolution 指南。

### 13. 双麦克风分工的可行性与架构边界

- 用户目标：同时使用两个麦克风；一个 USB/蓝牙麦克风记录会议，另一个专门记录用户与 TypeWhale/AI 的沟通及闪念胶囊信息。
- 可行性判断：macOS/Core Audio 支持同时使用多个输入设备；Apple 也提供 Aggregate Device（聚合设备）把多个物理设备组合为多通道输入。当前 `AudioRecorder` 已能通过 `AudioDeviceID` 绑定一个指定设备，因此 SDK 可以演进为每个物理设备一个独立 Capture Session（采集会话）。
- 目标拓扑：
  - Meeting Session（会议会话）：绑定会议麦克风，使用 long-form（长录音）策略、持续持久化和会议预览。
  - Personal Session（个人会话）：绑定近场/耳机麦克风，使用 conversation/idea（沟通/闪念）策略、独立 Provider Plan（服务提供器计划）和胶囊。
  - 两个 Session 分别拥有 `sessionID`、音频文件、Segment（转录片段）、Provider（服务提供器）、故障切换和 UI 状态，不能共享可变 transcript。
- 资源政策修正：麦克风 ownership（所有权）应默认为 `.exclusivePerDevice`（按物理设备独占），而不是“整个 SDK 只能有一个麦克风会话”。同一设备若被多个逻辑功能使用，应由一个采集所有者 fan-out（扇出）音频，不能重复打开硬件。
- SDK 需要新增：
  - `AudioDeviceLeaseManager`（音频设备租约管理器）：按设备 UID 分配和释放采集所有权。
  - 每设备独立的 `AudioCaptureSession`（音频采集会话）与 route observer（路由观察器）。
  - 不同采样率的独立标准化；如果需要跨设备时间对齐，再使用统一 monotonic clock（单调时钟）和 drift correction（时钟漂移修正）。
  - 本地模型执行仍受 Provider Scheduler（服务提供器调度器）限制；两路采集可以并行，但 SenseVoice 推理不一定并行。
- 两种设备实现路径：
  1. 不要求同步的独立会话：每个设备建立独立采集链路，会议与个人文本分别处理；这是推荐路径。
  2. 需要采样级同步：使用 Core Audio Aggregate Device（聚合设备）提供多通道输入，并处理统一采样率、主时钟和漂移修正；复杂度更高，当前业务不必默认采用。
- 硬件风险：蓝牙麦克风启用后，macOS 可能切换到包含麦克风的蓝牙通话模式，导致耳机播放质量和音量降低；蓝牙断连、profile（配置模式）变化和输入路由切换必须按单个 Session 处理。
- 产品风险：两个麦克风处于同一空间时都会听到会议内容。双设备只能区分“采集来源”，不能天然理解“这句话属于会议还是属于闪念”。推荐会议麦克风持续录制，个人麦克风通过快捷键/按住说话显式激活，或增加后续近场与说话人策略。
- 当前代码差距：现有 `SpeechInputCoordinator` 只有一个 `AudioRecorder`、一组 `activeSession` 和一套 VAD/preview 状态，不能直接支持双麦克风；新 SDK 的多 Session 与设备租约边界能够承载该能力。
- 官方依据：Apple Audio MIDI Setup 支持同时使用多个设备和多个 USB 麦克风；聚合设备要求一致采样率，并可为非主时钟设备启用 drift correction（漂移修正）。

### 14. 个人麦克风分配入口与非流式重叠窗口方案

- 用户补充：个人麦克风可以在设置中预先分配，也可以在胶囊上通过麦克风图标临时选择。
- 接口含义：SDK 保存默认 device role（设备角色）映射；具体 Session（会话）创建时允许 override（覆盖）输入设备。胶囊图标改变的是下一次或当前允许切换点的设备选择，不能在未定义切换边界时直接热换底层采集设备。
- 用户提出的 SenseVoice 非流式预览算法：
  1. 每约 `0.5s` 识别不断增长的当前音频，产生几个新字并累加展示。
  2. 累计到 `15s` 后识别完整窗口，与此前提取文本比较；发现错误则立即替换，无错误也用完整结果刷新。
  3. 下一轮使用约 50% overlap（重叠），例如 `7.5s–22.5s`，通过重叠区与前文对齐，维持连续和准确。
- Agent 判断：overlap-and-reconcile（重叠识别与文本对齐）方向合理，明显优于当前无重叠块的朴素拼接；但原始执行频率和“整体替换”范围需要调整。
- 原始方案风险：
  - 若每 `0.5s` 都重跑增长到 `15s` 的完整窗口，单轮累计需解码约 `232.5s` 音频；如果每 `7.5s` 再开启一个 50% 重叠周期，计算量进一步放大。
  - 纯字符串重叠在重复短语、标点修正、同音词和 ASR 增删字时可能对齐到错误位置。
  - 整体替换已经 finalized（确认）的前缀，会重新引入全文跳变；相同结果也重复发布，会产生无意义 revision（修订版本）和 UI 动画。
- 推荐的 two-lane（双通道）方案：
  1. Preview Lane（快速预览通道）：约 `0.5s` 接收新音频，只更新未确认 partial（临时结果）；latest-only（只保留最新请求），允许合并过时请求。
  2. Reconciliation Lane（校正通道）：使用固定上限窗口和 overlap（重叠），在 hop（推进步长）到达、VAD 停顿或结束时运行一次高质量识别，不在每个 0.5 秒 tick 都重跑完整 15 秒。
  3. Reconciler（对齐校正器）只修改未 finalized 的尾部；已确认 Segment（转录片段）保持不可变。
  4. 相同文本不重新发布，只提高稳定计数或推进 commit horizon（提交边界）；不同文本立即更新语义状态，UI 再决定使用何种受控视觉修正。
  5. 每个窗口保留左侧 overlap 上下文和右侧 guard region（保护区）；只提交远离窗口右边缘、且在连续识别中稳定的中段。
- 更可靠的对齐依据：sherpa-onnx 的 SenseVoice 结果可包含 tokens（词元）和 timestamps（词元起始时间）；当前 `TypeSpeakerNativeRecognizerTranscribe` 只复制 `result->text`，把 tokens/timestamps 丢弃。新 Provider（服务提供器）应先完整暴露这些字段，优先按时间轴对齐，再用文本相似度兜底。
- 稳定策略候选：Local Agreement（局部一致性），即连续两次识别输出中最长稳定公共前缀才进入 finalized；结合 token timestamps 可避免只靠字符位置判断。
- 参数建议：窗口、重叠和推进步长必须可配置并用真实录音评测。初始候选可比较 `15s window / 5s overlap / 10s hop` 与用户提出的 `15s / 7.5s / 7.5s`，不能在没有延迟、功耗和准确率数据前把 50% 重叠写死。
- 与当前代码关系：
  - 已有部分：首帧约 0.3 秒、后续约 0.5 秒快照；当前块约 10 秒软边界、18 秒硬边界；`committedPreviewText + latestPreviewText` 区分冻结前缀与可变尾巴。
  - 尚未实现：跨块 overlap、token/timestamp 输出、时间轴对齐、Local Agreement（局部一致性）、只校正未确认尾部、双通道调度和持久化 commit horizon（提交边界）。
  - SDK 草案已包含 partial/finalized 事件、Segment 模型和 Reducer（状态归约器），能够承载该算法，但此前尚未规定 SenseVoice Provider 内部采用哪一种窗口与对齐策略。
- 适用范围：该算法主要属于 Offline Snapshot Provider（离线快照服务提供器）；真正的本地流式和在线流式 Provider 应优先消费模型原生 partial/final 事件，不必重复做 15 秒音频重解码，但仍可复用统一稳定状态层。
- 研究参考：Whisper-Streaming 使用 Local Agreement（局部一致性）把离线模型转成实时系统；sherpa-onnx SenseVoice 示例公开了 text、tokens 和 timestamps；这些思路可借鉴，但必须用 TypeWhale/SenseVoice 真机数据重新评测。

### P-01：Whisper-Streaming 与 Local Agreement（局部一致性）

- 论文：*Turning Whisper into Real-Time Transcription System*（《将 Whisper 转化为实时转录系统》）。
- 作者：Dominik Macháček、Raj Dabre、Ondřej Bojar。
- 发表信息：IJCNLP-AACL 2023 System Demonstrations；arXiv 首次提交于 2023-07-27，修订于 2023-09-21。
- 论文地址：[arXiv:2307.14743](https://arxiv.org/abs/2307.14743)。
- DOI（数字对象唯一标识符）：[10.48550/arXiv.2307.14743](https://doi.org/10.48550/arXiv.2307.14743)。
- 论文直接支持：离线 Whisper 可以通过增量处理与 Local Agreement（局部一致性）策略构造成实时系统；论文报告在其未分段长语音测试条件下约 `3.3s` 延迟，并用于多语言会议现场转录。

### P-02：流式快速结果与第二阶段校正

- 作者：Haoran Zhou、Xingchen Song、Brendan Fahy、Qiaochu Song、Binbin Zhang、Zhendong Peng、Anshul Wadhawan、Denglin Jiang、Apurv Verma、Vinay Ramesh、Srivas Prasad、Michele M. Franceschini。

- DOI（数字对象唯一标识符）：[10.48550/arXiv.2506.12154](https://doi.org/10.48550/arXiv.2506.12154)。
- 论文直接支持：第一阶段使用带 causal mask（因果掩码）的 CTC（连接时序分类）解码器产生流式 partial（临时结果），第二阶段利用原 Whisper 能力重排或校正结果，说明低延迟显示与高质量收口可以采用不同处理阶段。

### L-01 / L-02：TypeWhale 当前实现证据

- `native/TypeSpeakerNativeASR.c`：`TypeSpeakerNativeRecognizerTranscribe` 当前从 sherpa-onnx 结果中复制 `result->text` 后销毁结果，没有把 tokens（词元）或 timestamps（时间戳）传给 Swift。这是新桥接迁移必须补齐的结构化数据缺口。
- `native/Sources/Infrastructure/Audio/AudioRecorder.swift`：当前已有首个快照约 `0.3s`、后续约 `0.5s` 的触发节奏，以及约 `10s` 软边界、`18s` 硬边界的当前块策略。

- 结论：论文和官方接口证明候选方向具有依据；本地源码证明现有实现尚未完成这些能力。两者之间仍需要迁移实现与 TypeWhale 专属基准测试，不能在文档中写成“已经支持”。

## 不同观点复盘

### 已经消除的分歧

#### 预览的定义

- 原误解：预览胶囊的视觉设计。
- 当前一致理解：预览相关代码的模型、调度、状态、生命周期和 Presenter 边界。

#### 改造方式

- 潜在旧方向：继续在 `SpeechInputCoordinator` 和 `CapsuleTextBuffer` 中局部修补。
- 当前一致方向：建立新模块，旁路运行，按明确边界逐段迁移。

#### 胶囊是否拥有最终文本

- 用户希望复用预览能力避免长录音结束后重跑整段识别。
- Agent 认为目标成立，但胶囊显示缓冲不能成为最终文本来源。
- 当前可兼容的方向：权威增量转录同时服务胶囊与最终输出。

#### 三种预览引擎的组合关系

- 原未决点：三种引擎是互斥选择、自动接力，还是并行交叉验证。
- 用户决定：单会话只激活一个主引擎，允许主引擎故障后切换备用引擎。
- 当前一致理解：这是带明确 ownership 转移的故障接管，不是多个引擎同时输出、投票或竞争。

### 仍然存在的不同观点或未决边界

#### 普通短口述的最终文本来源

- 路径 A：普通口述继续使用完整录音 final ASR，长录音使用增量转录。
- 路径 B：新架构成熟后，所有录音都使用权威增量转录作为最终结果。
- 当前 Agent 推荐：先采用 A 保护现有质量，再以真实准确率和延迟数据决定是否迁移到 B。

#### “一个新文件”还是“一个新模块”

- 用户表达：重新生成一个文件并逐步迁移。
- Agent 推荐：对外可以只有一个新入口文件，但内部必须是多个单一职责文件，避免形成第二个巨型协调器。

## 当前共识

1. 不在旧预览链路中继续堆叠补丁。
2. 新架构先建立在独立模块中，旧链路继续保护当前产品体验。
3. 非流式、本地流式、在线流式必须共享同一套上层转录状态和胶囊 Presenter。
4. 胶囊是权威转录状态的投影，不是文本数据库。
5. 新架构必须面向数小时录音设计，包括有界队列、增量持久化、崩溃恢复和最后一块收尾。
6. 预览迁移属于 P0 架构工作，但不扩大为整个 `SpeechInputCoordinator` 的一次性重写。
7. 任何迁移阶段都必须能够回退到旧链路，并验证普通短口述不退化。
8. 单个录音会话任一时刻只有一个主预览引擎；主引擎发生符合策略的故障时，允许把 ownership 明确转移给备用引擎。
9. 最终交付目标是可复用的语音转文字 SDK；Preview Window 是可选 UI 子模块，不能反向成为转录 Core 的依赖。
10. SDK 必须从接口层定义线程安全、事件顺序和访问 ownership；不能把“请只从主线程调用”作为默认正确性前提。
11. 最终设计必须提供 SDK 级完整公共接口与语义说明，不能停留在 `start/events/finish` 的演示级 API。
12. 英文架构抽象术语首次出现时必须紧跟中文释义；代码标识符保留英文，正文负责解释中文含义。
13. SDK 的麦克风独占范围应按物理设备划分；不同设备可以并行建立独立采集与转录会话，同一设备由一个采集所有者负责音频扇出。
14. 个人麦克风支持设置中的默认设备角色映射，并允许从胶囊入口选择或覆盖；实际采集仍由明确的录音/闪念触发流程控制。
15. 与预览算法有关的外部论文、官方接口和本地实现证据必须可追溯，并明确模型与实验边界；研究方向不能替代 TypeWhale/SenseVoice 真机验证。
16. SenseVoice 第一阶段采用方案 C：分块负责资源边界，跨块重叠负责文本接缝，Reducer（状态归约器）负责确认权威性。
17. 实验设置拆成“重叠校正预览（实验）”和“长录音增量输出（实验）”；后者依赖并自动启用前者，两个开关默认关闭。
18. 长录音模式不在停止后重识别整段音频；最终原文由已持久化确认片段与停止时校正尾部组装，但不得读取胶囊动画缓存。
19. 长录音实验保留完整原始音频、增量证据和回退路径；算法失败不能导致原始录音丢失。
20. 实施前必须形成正式设计规格与逐任务开发计划；计划必须包含测试先行、验证命令、回退点和文档更新。

2. 普通短口述最终是否永久保留完整录音 final ASR？

5. 数小时录音的主要交付形态是文件保存、主窗口长文档、剪贴板，还是仍然允许自动粘贴？
6. 增量转录需要保存哪些证据：音频块、原始候选、最终 Segment、时间戳和引擎信息？
7. SDK 第一阶段只承诺 macOS/Swift，还是从接口层开始保证 iOS 和无 UI 宿主也可接入？
8. 第一阶段是否允许同一进程同时运行多个 active transcription session；如果允许，麦克风、本地模型和在线 provider 分别采用什么资源并发上限？
9. 多个消费者订阅同一 Session 时，慢消费者的事件 buffer 是丢弃旧 partial、断开订阅，还是施加背压？

11. 双麦克风的两个 Session 是否共用一个本地模型执行槽；会议预览与个人沟通同时需要结果时，哪一路拥有更高识别优先级？
12. SenseVoice 非流式 Provider 的默认窗口参数采用 `15/5/10` 还是 `15/7.5/7.5`；需要用真实录音比较首字延迟、边界错误、CPU、内存和积压情况。
13. Local Agreement（局部一致性）需要连续两次还是三次一致才 finalized；停顿和会话结束时是否允许立即强制提交最后尾部？

## 2026-07-10：前十几秒准确时，后续校准是否仍有必要

## 2026-07-10：以一次长录音能力作为整体优化目标

- 用户判断：如果一次性长录音能够稳定完成，短录音自然不应再成为问题。
- 判断成立的前提：这里的“一次性”指用户只触发一次录音会话；内部仍必须使用 bounded incremental processing（有界增量处理）、confirmed segments（已确认片段）、mutable tail（可修改尾部）和 stop-time reconciliation（停止时收口），不能把整小时音频放进一个无限增长窗口。
- 产品目标：短录音是长录音链路的前缀。前 `20s` 必须保持 1.2 基线的即时反馈、流畅度和准确率；`60s`、`5min` 和 `1h+` 只增加有界的增量片段，不应出现越来越慢、越来越热或越来越不准。
- 技术验收：识别计算量随时长近似线性增长；快速预览不被校正长期阻塞；确认片段可持久化恢复；停止时尾部可收口；最终文本、智能整理和粘贴仍使用权威组装结果。
- 约束：不能用“扩大 1.2 累计窗口”“降低刷新频率但牺牲前 20 秒”“同时启动两个完整模型”作为默认解；这些方案可能改善单点指标，却会破坏短录音体验或放大 CPU 争用。
- 后续方向：先冻结 1.2.42 的短时体验基线，再设计统一的长录音增量引擎；短录音和长录音共用状态协议，但允许不同的窗口、提交和校正参数。

## 2026-07-10：确认文字缓存层与 UI 渲染层的职责边界

- 用户提出的设计认知是：应有一个负责处理和保存文字的缓存/状态层，页面只负责显示文字；如果页面只是读取已经准备好的内容，理论上不应因为文字处理本身而持续卡顿。
- 该认知的方向是正确的，但当前实现只完成了部分隔离，不能说已经存在完整的“文字缓存层 → 纯渲染层”结构：
  1. `native/Sources/Domain/RealtimePreview/PreviewTranscriptReducer.swift` 保存 `confirmedTokens`、`pendingCorrection`、`mutableTailText`、`displayRevision` 等权威转录状态，属于语义状态层，不是绘制缓存。
  2. `native/Sources/Presentation/Capsule/CapsuleTextBuffer.swift` 保存 `targetDraft`、`displayedDraft` 并负责首段淡入和 `75ms` 尾部推进，属于展示/动画状态，不是权威转录缓存，也不是 CoreText（文本排版）渲染缓存。
  3. `native/Sources/Presentation/Capsule/RecordingCapsuleView.swift` 仍在主线程的 `preferredSize`、`draw` 和 `attributedVisibleDraft` 中重复做字体测量、布局和带样式文本对象创建；`RecordingPanel.resizeAndPosition()` 也会在草稿更新时重复调整视图层级。
  4. Build 652 新增的 `CapsuleVisibleTextCache` 只缓存可见后缀的一部分宽度测量，不能复用完整的布局结果、`NSAttributedString` 或栅格图像，因此不是完整 Render Cache（渲染缓存）。
- 因此当前卡顿不是因为“缓存层完全不存在”，而是两个问题叠加：
  - UI 渲染层没有只消费已准备好的展示快照，仍在每次更新/绘制时重新测量和构造文本；波形更新也会触发整颗胶囊进入重绘路径。
  - SenseVoice/ONNX 推理在独立队列出现约 `194%` CPU 峰值，与主线程 CoreText 绘制竞争 CPU 和内存带宽；即使文字已经在缓存中，主线程仍可能被系统资源争用拖慢。
- 本次形成的架构判断：目标不是简单增加一个字符串缓存，而是明确分成 `Reducer（状态归约器） → Presentation Snapshot（展示快照） → Render Cache（渲染缓存） → View（视图绘制）` 四段。展示快照按 `displayRevision`、可用宽度和主题生成一次可绘制结果；View 只绘制该结果。波形与呼吸边框使用独立的兄弟视图/覆盖层，不能使文字快照失效；只有实际布局指标变化时才允许调整窗口尺寸。
- 当前结论：用户关于“页面只显示文字”的主观设计是正确的目标架构；现状并未完全达到。后续应优先把文字状态、展示快照、渲染缓存和波形绘制解耦，再单独治理 ASR 推理资源，不能把问题归结为单纯缺少缓存。
- 本次仅记录架构事实与判断，没有修改代码、没有构建、没有覆盖安装；当前安装版仍为 Build 652。

- 最终产品边界：预览只是实时反馈；最终识别、智能整理、保存和粘贴必须继续使用权威组装结果，不能为了让胶囊看起来流畅而牺牲最终文本。
- 当前波形重绘实验的正确定位：它是第一个最小、可回退的根因验证，用于确认“已有文字时的无效 `draw(_:)` 是否显著贡献卡顿”。无论实验成功或失败，都不能直接宣称核心问题已解决；结果必须决定下一项有证据的优化。
- 后续验收必须同时看四类结果：前 `20s` 的体验是否不退化、`60s/90s/1h+` 的延迟与卡顿趋势、最终文本与粘贴链路是否一致、主线程与 ASR 推理资源是否保持可控。若只改善绘制次数但长录音仍逐渐卡顿，实验应判定为局部有效而非完成。

## 2026-07-10：评估方案 A——显示接口流式化

- 用户提出方案 A：保留当前增量识别与 `confirmed + mutable tail`（已确认片段 + 可变尾部），把 Reducer（状态归约器）对 UI 的全量字符串输出改成 `appendStable`、`reviseTail`、`scrollCommit` 等事件流，并以稳定前缀、受控尾部和独立渲染节拍减少闪烁。
