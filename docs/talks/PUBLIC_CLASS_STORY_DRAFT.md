# 把一句话送进输入框，为什么这么难？

TypeWhale 开发历程与公开课故事底稿 · 第一版 · 2026-09-05

状态：供讲述者讨论的编辑稿，尚未定稿、尚未制作 PPT。不是产品规格或商业成功报告。本文由开发记录提炼，个人动机、情绪和现场回忆需由本人补充确认。

## 1. 这个对话里，我建议承担什么角色

我建议担任你的**开发历程采访者、故事编辑和公开课内容策划**。

采访者负责找回记录里没有留下的部分：当时为什么非做不可，哪次修改最让你失望，什么时候觉得这件事值得继续。故事编辑负责把日志转成人能理解的经历，保留起因、误判、反复和代价。内容策划负责把经历变成听众能带走的判断方法，最后再设计 PPT 的节奏、演示与转场。

你负责真实经历、价值判断和最终表达；我负责梳理材料、核证、追问和组织。这个角色定义是我的建议，等待我们讨论后确定。

我的工作原则是：戏剧性来自真实的矛盾和反转。不会编造你熬了多少夜、花了多少钱、想放弃多少次，也不会把日志中“某条技术路线被放弃”写成“你差点放弃整个项目”。

本轮范围是故事总结与讨论材料；不动产品实现、版本、构建、安装及历史记录正文。验收标准是你读完能挑出想讲的故事、指出不符合经历的描述，并知道下一轮该补什么。

## 2. 目前最值得讲的一条主线

**我以为是在做一个把声音变成文字的软件，后来发现，我一直在解决“软件怎样才算听懂一个人”。**

这是一句建议讲法，不是你的历史原话。

从功能描述看，TypeWhale 的主流程很短：按快捷键、说话、得到文字、送回正在使用的应用。真正进入日常使用后，麻烦藏在每一个“应该很简单”的地方。

不说话时，它可能自己听出几个字。说完了，最后几个字可能没跟上。让它润色，它可能开始回答你的问题；不许它乱改，它又可能干脆原样照抄。换了模型，交付结果还可能被旧缓存或兜底逻辑影响。测试全部通过了，实际听到的声音却已经不像原来的声音。

这段开发经历里最有张力的部分，是“每次修复都有理由，而有理由不代表真实体验会更好”。你不断用实际使用结果纠正实现方向，项目里的许多协作规则，也由此有了具体的意义。

建议课程围绕一个问题展开：**当 AI 很容易交出一个看似完成的结果，我们怎么判断它真的完成了？**

## 3. 八个可以讲给人听的故事

### 故事一：软件没听见人说话，却自己说了话

**发生了什么。** 7 月 21 日的记录里，静音会被识别成“我”“我想”“Yeah”等短文本。过滤已知词之后，又出现新的“我放。”。于是加入了规则：未知的两字短结果，要连续出现两次才放行。

**反转。** 真正说出的“结束”，在停止前只出现了一次，也被挡住了。这个规则随后被立即回退。

这段经历可以说得很朴素：为了让软件别瞎说，我们先让它少说；后来发现，它把人真的说过的话也吞掉了。判断是否说过话，不能只看那几个字像不像噪声，还需要音频证据。

**可以带走的认识。** 修复错误时，要同时检查有没有伤害正确的情况。一个“误报减少”的数字，可能藏着“真实内容丢失”。

**状态与出处。** 两次确认方案已回退；当时未知短幻觉仍待从音频层解决，不能讲成在这一轮彻底根治。见 [S1]。

### 故事二：我让它帮我说清楚，它却替我作主

**发生了什么。** 智能整理需要保留问题、否定、限制和人称。日志记录了提示词过度约束、短句污染、模型代答，以及“不能”改成“不得”后被程序误判、丢弃整理结果的问题。

**反复。** 规则越加越多，Qwen3 4B 把照抄原文当成最安全的选择。固定测试答案还曾被写进公共提示词，影响所有请求。模型能生成结果，也不意味着应用最后真的交付了这个结果。

**转折。** 后来把“表达整理”与“回答问题”分清；精简重复禁令；测试开始穿过真实生产路由，核对最终交付。7 月 27 日的特定回放中，45 次短句与结构测试没有失败，另有 18 次复杂场景回放没有失败。8 月 25 日仍继续修复润色代答边界，说明这不是一次提示词调整就永远结束的工作。

**建议讲法。** “我说‘这个模型为什么突然变慢了’，是想把这个问题发出去。它如果当场给我解释原因，就已经做错了工作。”

**可以带走的认识。** AI 的能力需要与角色匹配。对于输入工具，保留人的意思比展示聪明更重要。测试样例通过，也不等于所有日常说法都通过。

**状态与出处。** 多轮已实现与历史回放证据，不能宣称全面解决语义问题。见 [S2]。

### 故事三：测试说声音没问题，我的耳朵说不对

**发生了什么。** 克隆音色每句开头有短促杂声。换用短参考音频后，波形指标改善，四音色资格矩阵也通过。

**反转。** 用户试听发现，视频参考音色的声线变化无法接受。7 月 28 日 Build 862 回滚到此前相似度更高的参考，并明确后续要同时检查句首干净、首字完整、声线相似。

**建议讲法。** “噪声少了，测试绿了，可我想要的那个声音也变了。”

**可以带走的认识。** 测试能回答它被设计来回答的问题。声音像不像、动画顺不顺、话是不是自己的意思，都需要对应的体验验证。

**状态与出处。** 这是一次明确的产品回归与回滚，不能把被回滚的方案放进成功清单。后续还做了盲听收敛。见 [S3]。

### 故事四：忙了很多轮，最后决定把一批模型删掉

**发生了什么。** 项目探索过多种识别与朗读模型，做下载、运行时、测试和界面接入。7 月 26 日，六个 ASR 候选因本产品场景中的准确性、混合语言、响应、资源或依赖问题退役。7 月 28 日，本地 TTS 收敛到 ZipVoice。

**代价与决定。** 这些候选已经消耗了接入与验证工作，最终还是退出产品。日志记载，TTS 清理把约 43.08 GiB 的受管资源移入废纸篓，保留可恢复路径。

**建议讲法。** “有一段进展，是我终于知道哪些东西不应该继续留在软件里。”

**可以带走的认识。** 探索的产出可以是一份有依据的淘汰名单。模型选择要回答具体场景是否合适，不能把下载完成当成产品价值，也不能把本项目退役推导成模型普遍不好。

**状态与出处。** 路线退役与清理有记录；这不证明你当时想放弃整个项目。见 [S4]。

### 故事五：我说“保留那个体验”，它理解成了“换个颜色”

**发生了什么。** 候选胶囊有值得保留的展示体验。7 月 23 日 Build 804 把旧胶囊改成黑色，用户验收指出：这没有把候选胶囊的独立 UI 与展示体验转正。

**转折。** Build 805 回查历史实现，恢复对应的展示机制，同时不恢复整套候选运行链路。

**建议讲法。** “它确实变黑了，但我想要的不是只变黑。”

**可以带走的认识。** “跟以前一样”“更居中”“更流畅”都需要还原到可观察的行为。需求复述的价值，是尽早发现双方说的是不同东西。

**状态与出处。** 安装版静态视觉有复核；当时物理 Fn 录音、逐字推进和收尾动效仍留有实录验收项。见 [S5]。

### 故事六：一个程序修好了，两个程序一起用还是错

**发生了什么。** 语音输入临时写入剪贴板，Reader 将其当成用户新复制，导致胶囊反复吸附到鼠标。第一轮恢复来源标记，逻辑看起来合理。

**反转。** Build 870 真实联调仍失败：临时文本只存在约 0.3 秒，Reader 每 0.6 秒扫描一次，它可能只看见随后恢复的旧剪贴板。Build 871 才进一步识别恢复事件，同时保留用户主动复制新内容的行为。

**可以带走的认识。** 每个部分单独正确，还需要验证它们按真实时序放在一起会发生什么。真实使用暴露的是组合问题。

**状态与出处。** 后续协议与时序回归有记录；本文没有重新执行双应用联调。见 [S6]。

### 故事七：最有价值的一次优化，是找回本来就说过的话

**发生了什么。** 长录音在分块、校正和交付之间出现内容缺失。7 月 22 日用一段 129.657 秒的固定录音复查：整段识别为 751 字，当时分块校准结果为 749 字，历史故障缓存只有 638 字。

**有成就感的证据。** 这段样本恢复了 111 字。记录进一步核对音频区间的归属，避免只凭“看起来长了一点”认定成功。

**建议讲法。** “那次结果里多出来的 111 个字，是原本就应该交到我手上的内容。”

**可以带走的认识。** 可靠性可以直接对应人的表达劳动。让用户不用重说一遍，本身就有价值。

**状态与出处。** 一个固定样本的历史回放结果，不是全量准确率，也不能推导所有长录音都不会丢字。见 [S7]。

### 故事八：觉得它慢，最后发现每次都在重复做功课

**发生了什么。** 用户觉得本地整理反应不够快。日志定位到每次重新计算固定提示词的成本，而完整等待还包含生成与独立的发送倒计时。

**转折。** 复用安全的提示词前缀后，Build 826 安装包 Worker 的特定测试中，首轮首字约 579 ms，热态中位约 118 ms。随后还补缓存隔离、异常恢复和内存预算。

**可以带走的认识。** 性能优化先把等待拆开，确认时间花在哪里。一个明显的局部收益，也必须守住不串文、不重复交付的边界。

**状态与出处。** 这是特定机器与请求的 Worker 首字指标，不是从按键到粘贴的整链路速度，更不是所有用户都快五倍。见 [S8]。

## 4. 这段经历已经能提炼出什么价值

第一，是把表达送进真实工作流。语音识别之外，保留原意、回到正确应用、不抢焦点、不误发送，决定了工具能否融入工作。

第二，是形成了一套识别“假完成”的方法：下载成功不等于模型可用，模型输出不等于最终交付，编译通过不等于操作正确，自动指标通过不等于体验满意，本机安装成功不等于公开发行就绪。

第三，是学会带着证据改变方向。短词确认回退、音色回滚、候选模型退役，都能讲成有代价的选择。是否遗憾、是否松了一口气，需要你告诉我。

第四，是把使用反馈变成协作资产。现在的规则要求先澄清、保护旧体验、检查并发、真实安装验证、记录否决和未决事项。我们可以讲这些规则与哪些具体问题相呼应，但不能未经追溯就断言每条规则都由某一次事故直接产生。

目前证据支持的是产品价值与工程积累；还没有足够证据支持收入、用户规模、留存或商业成功。公开课可以讲“我认为它为什么值得做”，并把真实使用收益补进来。

## 5. 文档应该怎么整理，才能变成一场分享

以开发日志建立时间与事件索引，再用 Git、构建和专项材料核对关键转折，最后用现行文档确认哪些结论今天仍成立。旧日志常见倒序、补记与同 build 多条记录，不能用行数或版本号计算失败次数；现有 Git 最早可见提交为 6 月 18 日，日志有更早记录，也不能据此确定真实开工日。

每个入选故事只保留六项：当时想做什么、实际发生什么、为什么第一种办法不够、付出了什么、最终决定什么、听众能带走什么。技术名词放讲者备注，舞台上先讲具体行为。

下一轮请你标记：最像自己的三段、不符合事实的段落、最想补充的亲历时刻。我再补访谈，把故事缩成一条有起伏的课程线；之后才拆页、设计演示和制作 PPT。

## 6. 暂定的课程节奏

先用一句普通口述演示观众眼中的简单任务，再揭示背后的反复。主体建议挑三到四个故事深入讲，其余作短插曲，避免把八个故事平铺成修 bug 清单。

建议骨架：**一次有用的输入 → 修复反而带来新问题 → 发现完成标准出了偏差 → 学会验证和放弃 → 展示真正保住的价值。**

适合互动的地方：先让听众判断“两字短句要出现两次才放行”是否合理，再揭示“结束”被吞掉；或者先展示“测试全绿”，再问声音变得不像本人算不算成功。互动利用真实冲突，不制造虚假事故。

标题暂荐《把一句话送进输入框，为什么这么难？》。课程时长与听众未确认，暂不锁页数，不安排依赖未经排练功能的现场演示。

## 7. 下一轮最需要你补充的内容

1. 听众是谁、分享多少分钟，希望他们听完敢做什么或理解什么？
2. 最初哪个真实场景让你决定做这个软件？第一次完整输入成功时，你在哪里、在做什么？
3. 哪次反复最让你烦，哪次删除或回滚最舍不得？有没有真正想停下整个项目的时刻？
4. 哪个瞬间让你觉得值了？最好是一件具体事情，例如某段需求真的不用再手敲，而不是笼统的“效率提升”。

不需要一次回答全部。先选最有感觉的故事，我们就能继续。
