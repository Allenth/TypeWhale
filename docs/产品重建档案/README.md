## 目标

从 TypeWhale 项目启动阶段开始，逐步收集用户与 AI 的原始讨论、提示词和相关证据，复原每项功能从提出、调整、实现到验证的完整过程。最终将这些材料精简为一套可执行、可测试的产品重建档案，用来检验另一个 AI 能否据此重建出功能与体验相近的 TypeWhale。

这不是现行产品文档的替代品，也不直接证明某项功能已经实现。稳定结论仍须核对代码、Git、构建记录与真实验收，并按职责回填到 `docs/current/` 对应文档。

## 整理原则

1. **先保存，再提炼**：原始导出保持原貌，不在原文件中润色或重写。
2. **事实与推断分开**：用户原话、AI 回复、代码证据、后续推断分别标注，不能把推断伪装成历史事实。
3. **保留演变过程**：记录被否决、失败、撤回和被替代的方案，不只留下最终结果。
4. **保留产品信号**：用户对体验的满意、不满、担忧和优先级判断属于重要证据，不能被弱化成普通优化建议。
5. **状态必须明确**：区分“提出、讨论中、已决定、已实现、已验证、已否决、已被替代”。
6. **最终必须可执行**：精简后的材料要能指导开发，也要包含可观察的验收标准和失败条件。
7. **保护敏感信息**：账户凭据、密钥和私人数据不进入仓库；必要时只保存脱敏副本，并注明脱敏范围。

## 阅读排版标准

- 每份长文先给状态、范围和阅读路径，再展示正文。
- 清单和对比使用表格；连续过程使用编号；解释性内容保持短段落。
- 长对话按轮次折叠，默认只显示提示词导航，避免打开文件就看到文字墙。
- 原文与整理结论分区显示；原始导出中的摘要只负责导航，不代替原文。

## 本阶段完成标准

- 存档目标、证据边界和最终用途清晰。
- 原始材料拥有独立目录，不与后续整理稿混放。
- 任意一份新材料都能标明来源、时间、完整性和关联功能。
- 尚未核证的材料不会被写成当前产品事实。
